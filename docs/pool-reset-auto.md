# Pool reset timer

`app.pool_reset_auto` redeems one banked Claude reset when our own Anthropic accounts are about to run dry and a lane on the ordered list would pause. It runs as the systemd user timer `agent-lb-pool-reset-auto` on the primary, every 5 minutes, with no model request: the primary owns the accounts, holds their tokens and stores the limit readings.

## Rule (`app/pool_reset_rule.py`)

- When: the usable accounts of ours (owned by this agent-lb; teammate-owned accounts are never counted, Alex 2026-11-10: "focus on our traceabale usage") sum to 28 or fewer all-models points left, under 45 minutes are left at our last hour's pace, or none of ours is usable. That fires before Factory's 20-point floor for Alex's own chats trips; the floor reads the timer's `usable_points`, so it counts ours only too. Later is never worse for the points a reset frees, so it fires no earlier. Readings older than 15 minutes on a usable account of ours stop it.
- Only when a named lane would pause: the Rails back office's ordered lane list (`pool-pacing-lane-order/1` at `ax102:/home/jobs/.agent-rails/factory/pool-pacing/lane-order.json`, read over ssh from the primary, `--lane-order` for another path) must read cleanly and name at least one lane; otherwise the decision is `no_named_lane` and nothing is redeemed (scope "Factory usage balance", approved 2026-11-10: a reset only when a lane he named would pause).
- Cap: only an account of ours whose all-models week is at 95% or more (Alex: "at 95% please and only one per week", record alex-two-resets-this-week-2026-11-09), every week. In the week of Monday 2026-11-09 (weeks start Monday 00:00 America/New_York) six is the guard against a bug (record alex-overnight-full-approval-2026-11-09, its 03:43Z addendum: "reset fable when we need or swap to opus properly", as needed past two until the weekly turn on Nov 15); from the week of Nov 16, one a week (`app/core/claude_reset_week.py`). The cap counts redemptions on our own accounts only; one on a teammate-owned account is not ours. agent-lb's own Claude redeem path refuses past the cap, and on an account whose latest weekly reading is under 95% or missing, for every caller, counted from `reset_credit_attempts`. No second within 60 minutes of the last one, and none while the last one is unconfirmed. The timer passes `overrideDailyLimit` only for a later reset of the same week when the last one is under 24 hours old. When the pool is about to run dry with nothing worth spending, or at the guard, it sends one line and no more until the pool recovers. The older `agent-lb resets policy` job is retired and deleted.
- What a reset gives back: on 502ebd48 (2026-11-10 03:17Z) a reset cleared the Fable weekly window (39% to 0%) and all-models fell 100% to 81%. The pick is the owned account where a reset frees the most all-models points: its Fable weekly use times its own all-models-per-Fable ratio over the last 24 h, capped at the ratio measured on 502ebd48. Accounts that free under 10 points, hold no banked reset, or are teammate-owned are skipped. Teammate-owned accounts (pushed by a teammate's agent-lb, today Nate's 25600cac, 86fe250c and bfb49472) are never redeemed: only their owner holds the sign-in, and the primary's redeem path refuses an account it does not own. A yes file `pool-reset-auto/teammate-yes/<short id>`, written only on Alex's or the teammate's word, is noted in the run log but still does not let the primary redeem it.

## Run

- `--live` acts; without it a run is a dry run that prints the decision. `--readings <headroom copy>` and `--redemptions <list>` decide on copies and never act.
- Each live redemption goes through the dashboard route `POST /api/accounts/{id}/rate-limit-reset-credits/consume` after a read of `GET .../rate-limit-reset-credits`, so it uses the tokens agent-lb already holds. If the read fails (Anthropic answers the listing with 429 at times), nothing was consumed: it tries the next candidate, then sends one notice and tries again every tick. Anthropic limits its usage endpoint per account, and agent-lb's usage poller reads the same endpoint, so the consume's own status read can answer 429 seconds after a clean preview (2026-11-12 05:10Z). On a 429 from the preview, or from a consume that left no row in `reset_credit_attempts` for the account, the run waits 180 s once and tries the same account again, then moves to the next candidate; that 429 sends the retry notice and never writes a `hold` file. The run keeps to 390 s, inside the unit's 420 s limit, and shortens the confirmation wait to fit; an unconfirmed redemption is confirmed on a later tick from `pending.json`. Only a consume that fails another way, leaves an attempt row, or is not redeemed writes a `hold` file and reports. agent-lb logs the `Retry-After` and rate-limit headers of every failed reset call (`app.core.clients.anthropic_resets`) and puts `retry-after` in the error the timer records.
- Banked counts: agent-lb keeps them in memory, so a restart empties them. The timer keeps the last count it read per account in `held.json` and uses it when agent-lb has none; when the rule fires and finds no candidate it reads the missing counts with the preview. The consume checks the real inventory, so an old count can never spend a reset that is not there.
- After a redemption it waits for a lower reading in the account's weekly or Fable window before it sends one line with `t3 thread send` on ax102: a note to the Rails back office (for the morning report) and a queued message to Factory, carrying the time, the account, the points freed, the points left, how long they last at the last hour's pace and the resets still banked on our own accounts.

## State

`~/.agent-rails/factory/pool-reset-auto/` on the primary, mirrored to ax102: `runs.jsonl`, `last.json`, `pending.json` while a redemption awaits confirmation, and `receipts/`. A `hold` file in that folder on either host stops it.
